## 一、术语

- **Intake**：起草 plan 前对需求的结构化收口。**未答不起草**——五维清单任一空白不进入 drafting 状态
- **词汇步**：需求描述中的名词先映射 CONTEXT.md（领域术语契约）；不在表内的术语显式对齐（入 Pending 区或御定），**禁止以默认假设开工**
- **对齐（Alignment）**：调度者与主公就「同一组术语 + 同一组验收场景」描述一致。**不是「主公没说不行」**——后者是默认假设漂移
- **复述确认（Teach-back + Given-When-Then）**：调度者把需求用 Given-When-Then 验收场景复述给主公，主公确认后该 plan 才能进入 `aligned` 状态
- **Aligned 门**：plan 状态机新增的强制门——`drafting → aligned → ready-for-approval → executing`。Aligned = 主公已确认精确描述（不仅是「没问题」）

## 二、intake 五维清单（起草 plan 前的必答五问）

每条未答 = 该 plan 不进入 drafting 状态。

| 维度 | 问什么 | 答不出时怎么办 |
| --- | --- | --- |
| **范围** | 改哪些模块 / 路由 / 文件？哪些不动？ | 列「触及面 + 边界外声明」 |
| **深度** | 到代码层 / 接口层 / 行为层？是否触及契约？ | 列「改动深度 + 契约影响声明」 |
| **形态** | 重构 / 新增 / 修复 / 探针 / 文档 / 评审？单波多卡？ | 列「形态枚举 + 单卡/split 单卡」 |
| **边界** | 哪些绝对不动（已被既有契约锁死）？哪些是「先不动」但可激活？ | 列「红线 + 激活条件」 |
| **验收** | 完成判据是否机器可判？哪些命令 exit 0 / 文件须存在 / 指标须达标？ | 列「可跑验收 + unproven 项明示」 |

**硬门**：调度者委派协议（`dispatcher-roles-retrospective.md` §四委派协议）规定 brief 必须含五维——brief 缺一维 = 不派发，回 intake 补齐再走。本协议把委派协议要求从「背景完整」升级为「结构化五维」。

## 三、词汇步（需求名词先映射 CONTEXT.md）

### 3.1 步骤

1. **抽取名词**：从需求描述中抽取所有术语（含动词宾语、属性、状态、契约名）
2. **映射表查**：每个术语到 CONTEXT.md 找对应条目
3. **三态处置**：
   - **命中（preferred 词条）**：使用 preferred 词，禁用 `_Avoid_` 别名
   - **命中（_Avoid_ 别名）**：替换为 preferred 词；若用户坚持使用别名，必须显式声明
   - **未命中**：术语不在 CONTEXT.md → 进 intake「词汇 gap」环节（见 §3.2）

### 3.2 词汇 gap 处置

未命中术语处置三选项（必选其一）：

| 选项 | 触发条件 | 落地位置 |
| --- | --- | --- |
| **入 Pending** | 复用次数 <1，定义模糊 | CONTEXT.md §Pending 区（草案态） |
| **御定晋升** | 复用次数 ≥1，主公确认 | CONTEXT.md Language 区（晋升态） |
| **非承诺备注** | 仅本 plan 一次性使用，不期望复用 | plan 文档「局部词汇」段（不入仓契约） |

**硬门**：plan 模板必填段「词汇映射表」——表内每条术语标三态之一。无此表的 plan 不进 `aligned` 门。本协议把 CONTEXT.md 的「产出物零 `_Avoid_` 别名」从结果约束升级为流程前置。

## 四、需求对齐协议（统一语言背景下的精确描述）

### 4.1 「对齐完成」的定义

**对齐完成 ≠ 「主公没反对」**。对齐完成 = 双方对以下三项描述一致：

1. **同一组术语**：§三词汇步后双方用同一份词表（CONTEXT.md + plan 内词汇映射表）
2. **同一组验收场景**：Given-When-Then 形式写出的可跑场景集合
3. **同一份完成判据**：每条验收场景对应一个机器可判的 PASS/FAIL 判据

### 4.2 Given-When-Then 复述确认流程

调度者完成 intake 五维 + 词汇步后，向主公发出**复述确认**消息。模板：

```text
【复述确认 / Teach-back】
需求：[原始需求一句话]
意图：[我理解的真实意图]

术语（已映射 CONTEXT.md）：
- <术语 1> = CONTEXT.md <条目>（preferred）
- <术语 2> = 入 Pending（理由）
- <术语 3> = 局部词汇（一次性）

验收场景（Given-When-Then）：
- GIVEN <前提>
  WHEN <动作>
  THEN <可观察结果>
- ...

完成判据（机器可跑）：
- <命令 / 文件存在 / 指标> → 预期值

请确认：「以上描述是否与你意图一致？」或指出偏差。
```

主公回应「一致」/「以上偏差 X」/「补充 Y」三态之一。**「一致」**= 该 plan 进入 `aligned` 状态。

### 4.3 偏差处理

- **指出偏差**：调度者修订 plan，回到 §4.2 重发复述确认
- **补充**：调度者把补充项纳入五维 + 词汇步，回到 §4.2 重发
- **沉默**：**不算对齐**——对齐必须显式确认。沉默处理为「未对齐」，回到 intake 阶段

**硬门**：plan 状态机的 `aligned` 门（见 §五）。状态行必填枚举固定：未标 `aligned` 不进 `ready-for-approval`。

## 五、plan 状态机（`aligned` 门为强制门）

```
drafting ──────→ aligned ──────→ ready-for-approval ──────→ executing
   ↑              │                    │                       │
   │              │                    │                       │
   └────── 修订 ◀──┴──── 偏差 ◀───────┴──────── 主公裁决 ──────┘
```

### 5.1 状态转换条件

| From | To | 触发 |
| --- | --- | --- |
| (none) | drafting | 调度者起草 plan 完成五维 + 词汇步 |
| drafting | aligned | 主公复述确认「一致」 |
| aligned | ready-for-approval | 主公给最终审批（含范围/深度/形态确认） |
| ready-for-approval | executing | 主公下达执行令（如 `/goal 执行计划`） |
| executing | (none) | 工单完成 + 终验 ACCEPT（落地 W-V 报告） |
| * | drafting | 任意修订触发回 drafting；需重走 aligned 门 |

### 5.2 状态行契约

plan 文档必须含状态行（紧跟标题）：

```markdown
- 状态: **aligned**（<YYYY-MM-DD 主公复述确认>）/ **ready-for-approval** / **executing** / **done**
```

未标 `aligned` 直接进 `ready-for-approval` = 流程违规，commit-msg hook 的 Plan: footer 校验不应放过（见 §八硬化路径）。

**硬门**：plan 模板状态行枚举固定（`drafting | aligned | ready-for-approval | executing | done`）——其他值视为格式错误。本协议把 `ulw-quality-hardening-opt-20260922.md` §九 v2.2 的「审批语义升级」从单点裁决沉淀为契约。

## 六、事实依赖显式化

### 6.1 「待确认分叉」三必填

plan 内任何「待 X 事实确认后触发 Y」的分叉声明，必须含三项：

1. **触发判据**：什么观察/数据/事件会触发 Y
2. **悬置成本**：等待期间的实际代价（时间 / 资源 / 风险）
3. **降级路径**：若触发永远不到，plan 怎么收口

### 6.2 三态处置

| 三必填完整度 | 处置 |
| --- | --- |
| 三必填齐全 + 触发判据可观察 | 保留为「承诺型分叉」 |
| 三必填齐全 + 触发判据不可观察 | 降级为「非承诺备注」+ 不进 plan 状态机 |
| 三必填不全 | 不进 plan 草案——回到 intake 补齐 |

### 6.3 实例校正

`ulw-font-preload-sw-fetch-20260914.md` v1 写预案 B 但缺三必填中的「触发判据 + 悬置成本」（仅写「第二轮偶发报告」未量化）。**校正后**：

| 字段 | 校正后写法 |
| --- | --- |
| 触发判据 | 「连续 N 次生产构建观察到 `link rel=preload` 警告」+「N 次实测窗口数据」 |
| 悬置成本 | 「8 天日历空载 + 调度者注意力占用 + 期间同类预警被淹没」 |
| 降级路径 | 「若 30 天无新事实 → 标 `deferred`，进 deferred 池，主公裁决是否独立 plan 重启」 |

**硬门**：plan 模板必填段「事实依赖表」——每条「待 X」必须三必填齐全。本协议把 §六.2-5 从「沉淀方向」升级为机械模板约束。

## 七、调研路径顺序（「为什么类」问题）

### 7.1 三级证据优先级

| 级别 | 渠道 | 何时用 |
| --- | --- | --- |
| **L1 外部已知证据** | 上游 issue tracker / 官方文档 / 学术论文 / 行业实践 | 「为什么 X 会发生」「X 在何处被讨论」类问题 |
| **L2 内部复现矩阵** | 自建探针 / 多场景脚本 / A-B 对照 | 「X 在本仓是否触发」「触发条件具体是什么」类问题 |
| **L3 启发式推断** | 经验类比 / 模型迁移 | 仅在 L1+L2 不可得时降级使用，必须标 `[inferred]` |

### 7.2 调研类工单的硬性执行序

「为什么类」问题的标准执行序：

1. **L1 先行**：先检索外部已知证据（必须跑——不能用「找不到就跳过」糊弄）
2. **L2 确认**：内部复现矩阵作为「本仓是否复现」的**确认手段**，而非「发现手段」
3. **L3 兜底**：仅当 L1+L2 不可得时才允许启发式推断，结果标 `[inferred]`

### 7.3 反模式

- **「没找到外部证据 → 直接进内部复现」**：违反 L1 先行
- **「内部复现矩阵 = 发现手段」**：把确认手段当发现手段 = 漂移
- **「启发式推断不标签」**：违反 measured/inferred 分类学

### 7.4 本波实证

`ulw-font-preload-sw-fetch-20260914.md` v1 即走 L2 内部复现矩阵（多场景链路观察），但**漏走 L1**——Chromium 已知 preload warning 行为检索未做。8 天后（`ulw-font-preload-residual-20260922.md`）才回到 L1 找到上游结论。**校正后**：任何「为什么」类调研必须 L1 先行，无外部证据检索报告的 plan 不进 `aligned` 门。

**硬门**：调研类工单的 plan 必含「L1 外部证据检索报告」段（≥1 条引用 + 检索时间戳）——缺失则不进 `aligned` 门。本协议把 §六.2-6 的「外部证据检索先行」从沉淀方向升级为模板约束。

## 九、协议检查点（自检清单）

每个新 plan 起草完成时，调度者自检：

- [ ] §二 五维全部有答案（无空白）
- [ ] §三 词汇映射表完整（三态处置明确）
- [ ] §四 Given-When-Then 验收场景至少 3 条（happy + edge + regression）
- [ ] §五 状态行枚举合法（drafting/aligned/ready-for-approval/executing/done 之一）
- [ ] §六 每条「待 X」三必填齐全
- [ ] §七 「为什么类」问题 L1 检索报告已附（≥1 引用 + 时间戳）
- [ ] §八 落地动作清单（哪条硬化路径）
- [ ] §九 自检清单全过

未过清单的 plan 不进入 `aligned` 门。
